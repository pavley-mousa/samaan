# المعمارية

## المكونات

- `apps/storefront`: تطبيق Next.js + TypeScript لواجهة العميل ولوحة إدارة متاحة داخل نفس الموقع.
- `apps/api`: تطبيق NestJS + TypeScript لقواعد العمل والمصادقة وواجهات REST.
- `packages/shared-types`: أنواع مشتركة عند الحاجة، دون مشاركة منطق حساس بين العميل والخادم.
- PostgreSQL: قاعدة البيانات الأساسية.
- خدمة تخزين ملفات/صور: صور المنتجات والصور المرجعية للتفصيل، مع فصل الملفات الخاصة عن العامة.

## مبادئ التصميم

1. الخادم هو المصدر الموثوق للأدوار والأسعار والمخزون وحالات الدفع والطلبات.
2. تقسيم الـ API إلى وحدات: Auth, Users, Catalog, Pricing, Inventory, Cart, Orders, Tailoring, Wholesale, Shipping, Payments, Promotions, Reports, Audit.
3. استخدام migrations لإدارة تغييرات قاعدة البيانات.
4. حفظ المبالغ بدقة عشرية أو بوحدات نقدية صحيحة وفق تصميم العملة، وليس `float`.
5. تنفيذ تأكيد الطلب وحجز المخزون داخل transaction مناسبة، مع قفل/تحقق يمنع تجاوز المخزون.
6. التحقق من ملكية الموارد: العميل لا يقرأ طلبًا لا يخصه.
7. معالجة أحداث مزودي الدفع والشحن بصورة idempotent.
8. لا يتطلب الإصدار الأول Redis أو خدمات مصغرة؛ يبدأ كتطبيق API منظم، ويمكن إضافة مكونات عند وجود سبب.

## تسجيل الدخول والأدوار

- حسابات المستخدمين تحمل دورًا أمنيًا مثل `customer` أو `admin`، يحدده الخادم.
- لا تسمح واجهة التسجيل باختيار دور المدير.
- إنشاء أول مدير يكون عبر seed/أمر إداري آمن أو إعداد تشغيل محمي، وليس من مسار التسجيل العام.
- بعد نجاح الدخول يعيد الخادم هوية المستخدم والدور ضمن آلية الجلسة الآمنة.
- تستخدم الواجهة الدور لعرض عناصر UI فقط؛ وتفرض الـ API الصلاحيات نفسها على كل عملية حساسة.

## الجلسات

يُختار تنفيذ جلسة آمنة باستخدام ملفات تعريف ارتباط `HttpOnly`, `Secure` في الإنتاج، و`SameSite` مناسب، أو آلية موثوقة مماثلة. تجنب حفظ رموز طويلة العمر في `localStorage`. يلزم ضبط CORS وCSRF حسب آلية الجلسة.

## بيئات التشغيل

- Development: إعدادات محلية وأسرار تجريبية فقط.
- Test: قاعدة بيانات منفصلة وبيانات اصطناعية.
- Production: أسرار من environment/secret manager، HTTPS، مراقبة، ونسخ احتياطي دوري.
